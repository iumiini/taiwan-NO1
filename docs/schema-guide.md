# 圖鑑資料契約導覽

這份文件解釋 `schema/` 底下四個 Schema 為什麼這樣切、每個欄位從哪來。
設計依據為 Notion《台股寶可夢 — 設計討論總結》第五、六、十、十二、十三章。

---

## 為什麼要拆成四個檔

圖鑑是**單一真相來源**，遊戲與圖鑑網頁都只是它的消費者。
但裡面的資料**更新速度差很多**，混在一起會讓玩家每天重抓一大包沒變的東西：

| 檔案 | 內容 | 多久變一次 | 大小級距 |
|---|---|---|---|
| `index.json` | 索引／雜湊 | 每日 | < 1 KB |
| `species.json` | 種族值、屬性、稀有度、招式池 | 財報季／賽季 | 大 |
| `daily/YYYY-MM-DD.json` | 氣場、均線天氣、盾、收服成本 | 每個交易日 | 中 |
| `balance.json` | 克制表、稀有度參數、經濟數值 | 調平衡時 | 小 |

遊戲端每天只要抓 `index.json`（1 KB），比對 `sha256` 就知道哪些檔要重抓。
種族層整季不變 → 一季只下載一次。

這個切法直接對應設計文件第 13 節的變動性總表：**慢速層（種族值）與快速層（當日狀態）分開存放**。

---

## 兩層資料如何合體

畫面上一隻怪獸的數值，是三份資料相乘的結果：

```
最終能力 =（種族值 + 個體值）× 等級成長 × 當日狀態
           └ species.json ┘  └ 玩家存檔 ┘  └ daily.json ┘
```

- **`species.json` 決定形狀**（牠是什麼樣的怪）
- **玩家存檔決定大小**（練到幾等、烙印多好）—— 存在手機，雲端永遠碰不到
- **`daily.json` 只進乘區**（今天的天氣），永不改動面板

第 12 節的定案是「每日股況只從乘區進場，永不改面板」。Schema 用檔案邊界把這條規則變成**結構上不可能違反**：`daily.json` 裡根本沒有 `base_stats` 欄位可以寫。

## 六圍欄位對照

`species.json` → `base_stats`：

| 欄位 | 中文 | 來源數據 | 端點 |
|---|---|---|---|
| `hp` | 生命 | 營收規模 | TWSE `t187ap05_L` |
| `atk` | 物攻 | EPS | TWSE `t187ap06_X_ci` |
| `matk` | 魔攻 | 營收 YoY | TWSE `t187ap05_L`（官方直接給） |
| `def` | 物防 | 負債比（反向） | TWSE `t187ap07_X_ci` |
| `mdef` | 魔防 | 波動率（反向）＋殖利率 | 富果 K 線自算 ＋ TWSE `BWIBBU_ALL` |
| `spd` | 速度 | 周轉率 | TWSE `FMSRFK_ALL`（官方直接給） |

六圍總和必須等於該稀有度的 `bst`（面積由階層決定，同階只差形狀）。
`tools/validate.py` 會強制檢查這條 —— Schema 本身表達不了跨欄位加總。

## 每日層的四個子系統

`daily.json` 裡每隻怪有四組互不重疊的狀態，各自管不同的事：

| 欄位 | 看什麼 | 管什麼 |
|---|---|---|
| `aura` | 量價關係 | 遭遇與收服鑑定 |
| `weather` | 均線位置 | 戰鬥 buff（攻） |
| `kd` | KD 交叉 | 戰鬥減傷（守） |
| `net_value_shield` | 股價淨值比 | 血量墊＋爆擊免疫 |

系統邊界刻意不重疊（第 8、15、16 節）：**氣場管遭遇、均線管攻、KD 管守、PB 管盾**。

### 氣場四象限

`aura.quadrant` 由「當日漲跌方向」×「量能比（當日量÷近 20 日均量）」決定：

| | 量增（ratio > 1） | 量縮（ratio < 1） |
|---|---|---|
| **價漲** | `true_surge` 🔥 真暴走 | `phantom_surge` 👻 幻影暴走 |
| **價跌** | `true_weak` 💀 真虛弱 | `dormant` 🌙 蓄力假寐 |

範例檔的 2026-08-05：台積電漲 3.66% 但量能比 0.83 → `phantom_surge`。
規則書設計的「騙局個體」在真實資料上直接成立。

## 平衡參數為什麼要上雲

`balance.json` 放克制倍率、稀有度參數、收服成本係數、醫院費率。
把這些放進雲端而不是寫死在 Unity 裡，是為了達成第六章的設計意義：

> StatMapper 上雲 —— 平衡調整改雲端公式當天生效，玩家不用更新 App

同理，`daily.json` 的 `multipliers` 是**雲端算好的結果**而不是原始訊號。
遊戲端不需要知道「站上 5 日線要加多少爆擊」，只要照著乘區算傷害。
公式改了，隔天玩家開遊戲就生效。

`status` 欄位標示成熟度：`draft`（提案未驗證）／`playtest`（測試中）／`locked`（定案）。
目前所有數值都是 `draft`。

## 版本規則

`schema_version` 採語意化版本：

- **修訂號**（0.1.0 → 0.1.1）：修描述、補選填欄位 —— 舊版遊戲照常運作
- **次版號**（0.1.0 → 0.2.0）：新增必填欄位 —— 舊版遊戲要更新才能讀
- **主版號**（0.x → 1.0）：欄位改名或刪除 —— 破壞性變更

Phase 1 期間停在 `0.x`，欄位還會動。等第一版遊戲上架再升 `1.0.0` 並凍結。

## 目前的已知缺口

寫這份 Schema 時實測發現，以下欄位暫時填不出真值：

| 欄位 | 問題 | 暫時作法 |
|---|---|---|
| `source_metrics.eps` | 2026Q2 財報未到公布期，`t187ap06_X_ci` 僅 4 筆 | 由收盤價 ÷ 本益比回推 |
| `source_metrics.book_value_per_share` | 同上 | 由收盤價 ÷ 股價淨值比回推 |
| `source_metrics.debt_ratio` | 同上，`t187ap07_X_ci` 僅 4 筆 | **無替代來源，待解** |
| `source_metrics.market_cap` | 需股本，來源同樣受阻 | 待解 |
| `valuation.market_cap` | 同上 | `null` |
| `moving_averages.ma60` | 本次回補只算 5/20/240 | `null` |

季報端點是**滾動的當季快照**，不是全量歷史 —— 管線必須保留上一季資料作為 fallback，
否則每季財報公布前種族值會整批消失。這點原設計文件未涵蓋。

## 資料源陷阱

實測踩到的坑，寫在這裡避免重複：

1. **成交量單位不一致**
   富果 `snapshot` 的 `tradeVolume` 單位是**張**，`historical/candles` 是**股**。
   不可混用 —— 氣場的量能比若分子分母來自不同端點會算錯。

2. **snapshot 是 14:00 快照，不含盤後定價交易**
   與 `historical/stats` 的全日成交量約有 10% 落差。每日結算請固定用同一個來源。

3. **富果歷史 K 線單次上限「未滿一年」**
   跨度達一年即回 400。年線需 240 個交易日 ≈ 350 日曆日，剛好卡在邊界 —— 必須分段抓。

4. **`FMSRFK_ALL` 是 6.6 MB、需約 80 秒**
   timeout 設太短會拿到截斷的 JSON 而不是錯誤碼，容易誤判成端點壞掉。

## 怎麼用

```bash
pip install jsonschema

# 驗證範例檔
python3 tools/validate.py

# 重新產生索引（改動任何資料檔後都要跑）
python3 tools/build_index.py examples
```

`tools/validate.py` 除了 Schema 結構檢查，另外驗四條跨欄位規則：
六圍總和 = BST、BST 與稀有度一致、招式解鎖等級不超過等級上限、
遭遇基礎率總和 = 1、每日層的怪都在種族層有定義、淨值盾階層與 PB 一致。
